## 1. 目标

本次按照“机器狗可部署”的要求，将原来的 Python 原型改写为 ROS Noetic C++ 节点。整体思路是：

1. 先用 FAST-LIVO2 离线建图，得到先验点云地图。
2. 机器狗运行时不再依赖完整 FAST-LIVO2 建图流程，而是加载先验地图做定位。
3. IMU 负责高频姿态传播和高频位姿输出。
4. LiDAR 当前帧与先验地图做低频匹配，作为校正约束修正位姿。
5. 相机当前先作为曝光/欠曝质量门控，后续可继续加入特征重投影约束。

> 说明：用户说“C语言”，但 ROS Noetic 的消息、PCL、Eigen 工程生态实际对应的是 C++ ROS 节点，因此这里实现为 C++，更适合后续部署到机器狗工控机。

## 3. 核心算法原理

### 3.1 状态量

当前 C++ 版本使用简化 15 维误差状态：

\[
\delta x = [\delta p, \delta v, \delta \theta, \delta b_a, \delta b_g]
\]

其中：

- `p`：机器狗在先验地图坐标系下的位置。
- `v`：速度。
- `R`：机器狗姿态。
- `ba/bg`：IMU零偏。

### 3.2 高频IMU传播

节点订阅 `/livox/imu`，默认约 200Hz。每帧 IMU 到来后都会发布：

- `/dog_livo/odom_high_rate`

为了避免 MID360 板载 IMU 直接裸积分导致 Z 轴快速漂移，当前默认：

- 使用陀螺仪进行高频姿态传播。
- 不直接用加速度进行长时间位置积分。
- 位置主要由低频地图匹配修正。
- 启动时使用静止 IMU 平均加速度做重力方向初始化。

对应配置：

```yaml
imu:
  initialize_gravity_from_imu: true
  init_imu_samples: 200
  use_acc_for_position: false
  velocity_damping: 0.98
```

### 3.3 LiDAR到先验地图匹配

当前帧 `/livox/lidar` 点云处理流程：

1. 雷达点通过外参转到 `base_link`。
2. 去除太近/太远点。
3. 体素降采样。
4. 限制参与匹配点数，降低机器狗端算力压力。
5. 将当前点按当前位姿投到地图系。
6. 用 KDTree 在先验地图中找最近邻。
7. 构造点到点残差并做鲁棒加权。
8. 解 6 自由度位姿修正。
9. 发布 `/dog_livo/odom_corrected`。

残差形式：

\[
r_i = p^{map}_{nearest,i} - (R p^{body}_i + t)
\]

雅可比近似：

\[
H_i = [I, -R[p_i]_{\times}]
\]

### 3.4 相机约束现状

当前 C++ 版本只做相机质量门控：

- 统计过曝比例。
- 统计欠曝比例。
- 图像质量不好时降低匹配权重。

后续若要满足“相机、雷达、地图匹配共同作为 EKF 约束”，建议继续加入：

- ORB/FAST角点特征。
- 地图点投影到图像的重投影残差。
- 或者图像边缘和点云边缘的对齐残差。

### 5.3 结论

当前 C++ 算法已经证明以下可行性：

1. 能在 ROS Noetic 下编译运行。
2. 能直接读取 FAST-LIVO2 输出的 PCD 先验地图。

1. 还没有可靠的初始位姿对准模块。
2. 当前是点到点匹配，不如点到面/NDT在走廊结构里稳定。
3. 相机目前只是质量门控，还没有形成真正视觉几何约束。
4. 没有使用机器狗自身腿部里程计/关节里程计作为平移预测。

当前推荐机器狗端默认参数为：

```yaml
lidar_update:
  update_every_n_scans: 5
  scan_voxel_size: 0.45
  max_scan_points: 160
  min_effective_points: 50
  max_iterations: 1
  max_update_time_ms: 35.0
```

含义：

- MID360 点云约 10Hz，`update_every_n_scans: 5` 代表约 2Hz 做一次地图匹配修正。

1. 初始位姿对准：没有正确初值时，局部地图匹配容易收敛到错误位置。
2. 点到面/NDT约束：点到点最近邻在走廊和重复结构里不够稳。
3. 机器狗腿部里程计：IMU只适合高频姿态传播，平移预测最好由腿部里程计提供。


## 10. 精度提升实验与论文式算力评估

### 10.1 精度提升路线

本轮尝试了三类地图匹配约束：

1. `point_to_point`：当前点与先验地图最近邻点构造三维残差。
2. `point_to_plane`：用地图近邻PCA拟合局部平面，构造点到面残差。
3. `hybrid`：点到面作为主约束，同时加入弱点到点约束抑制沿平面滑移。

实验发现：

- 点到面残差数值更小，但在走廊/墙面/地面等大平面场景中，沿平面切向约束弱，轨迹反而容易滑移。
- 混合模式仍未明显优于点到点，而且CPU占用更高。
- 当前数据集上最稳定的是 `point_to_point + 300点 + 2Hz修正`。

因此当前默认配置改为：

```yaml
lidar_update:
  registration_method: "point_to_point"
  update_every_n_scans: 5
  scan_voxel_size: 0.45
  max_scan_points: 300
  min_effective_points: 50
  max_iterations: 1
```

### 10.2 参数扫描结果

使用 loop3 前30秒做快速参数扫描：

| 160点，每5帧更新 | 1.355 | 2.972 | 1.961 | 43.714 | 0.307 | 9.46 | 26.46 |

### 10.4 经典论文常用算力评估指标

后续写论文或给老师汇报时，建议至少报告以下指标：

| 类别 | 指标 | 含义 |
| --- | --- | --- |
| 精度 | ATE RMSE | 有真值轨迹时，估计轨迹与真值轨迹的均方根误差 |
| 精度 | RPE | 相邻时间段的相对位姿误差，反映局部漂移 |
| 精度 | 首尾同点误差 | 开始和结束回到同一地点时的位置差，适合当前实验 |
| 精度 | 地图匹配残差 | 当前帧点云到先验地图的平均最近邻残差 |
| 实时性 | 输出频率 | 高频位姿和低频校正位姿的发布频率 |
| 实时性 | 单帧处理耗时 | 每次LiDAR-map update耗时，常报告mean/max |
| 算力 | CPU占用 | 平均CPU和峰值CPU |
| 内存 | RSS内存 | 进程常驻内存，反映部署内存需求 |
| 地图规模 | Map points | 先验地图点数，影响KDTree内存和查询耗时 |

当前没有GNSS/动作捕捉真值，所以还不能严格报告 ATE/RPE。当前报告里的“首末窗口误差”只能作为闭环同点一致性指标。

### 10.5 当前精度瓶颈判断

loop3 在最终配置下首末窗口误差约 0.483m，说明参数优化有效。loop4 仍约 3.475m，说明精度瓶颈不只是匹配点数，可能包括：

1. loop4 与 loop2 先验地图重叠不足或起点初始位姿不够准。
2. 当前算法没有全局初始化，只能在初值附近局部匹配。
3. 只有LiDAR点到点局部约束，没有腿部里程计提供平移预测。
4. 走廊/楼梯等结构重复区域存在局部最近邻误匹配。

下一步精度提升建议：

1. 加初始位姿对准：人工初值、NDT粗配准、AprilTag或RTK给初始位置。
2. 加先验地图局部子地图：根据初值只加载半径10~20m地图，避免远处错误最近邻。
3. 加腿部里程计/轮速计/视觉里程计作为高频平移预测。
4. 将点到点改为带退化检测的约束：走廊退化方向降低LiDAR权重，非退化方向正常更新。
5. 有GNSS或人工测量真值后，正式计算 ATE RMSE / RPE，而不是只看首尾同点误差。
